# Taxonomy 快照生命周期与迁移审计

状态：第 1 阶段技术规则
规则版本：`0.1`
最后修订：2026-09-06

## 1. 目的

PhilPapers taxonomy 可能新增、删除、改名或移动分类。一次成功取得的完整快照只能证明取得时刻的
分类结构，不能被当作永远不变的分类表。本规则规定如何保留旧快照、比较新旧快照、判断私人兴趣
画像受到的影响，以及在什么条件下可以启用新快照。

本流程只审计受控分类的身份和结构，不评价论文，不扩张用户研究兴趣，也不替用户确认迁移。

## 2. 身份原则

- `category_id` 是分类身份的主要键；
- 分类名称是供人阅读的属性，不是唯一身份；
- 同一 ID 改名仍然是需要记录的 taxonomy 事件；
- 旧 ID 消失而新 ID 使用相同名称，只能产生人工复核候选，不能自动认定为迁移；
- 名称相似、共同词语或相同父分类不能单独证明两个 ID 表示同一分类；
- 合并、拆分或替代关系只有在官方数据或人工复核提供充分证据后才能登记。

## 3. 快照保留

每次取得并通过完整性验证的 taxonomy 使用包含取得时刻和来源字节哈希前缀的独立文件名：

```text
philpapers-taxonomy-YYYYMMDDTHHMMSSZ-<source-hash-prefix>.json
```

写入规则：

- 新文件先写临时路径，重新加载并验证后才原子发布；
- 旧快照不得因新快照导入而删除或覆盖；
- 相同路径和相同字节的重复导入是幂等操作；
- 相同快照 ID 对应不同规范化字节时视为路径冲突，保留旧文件并失败；
- 原始浏览器下载文件与规范化快照分开管理；程序不自动删除原始下载；
- 快照属于受条款约束的本地缓存，默认位于 Git 忽略的 `var/taxonomy/`。

历史兴趣画像记录 `taxonomy_snapshot_id`。补跑需要旧 taxonomy 时，只能按该稳定 ID 在当前
taxonomy 目录中解析预期文件名、重新验证并使用；不能退回当前快照，也不能按“最接近的日期”猜测。

## 4. 审计输入

`pfm taxonomy-audit` 需要：

- `--old`：私人配置当前实际指向的已验证快照；
- `--new`：新取得并已验证的候选快照；
- `--config`：当前私人 watchlist。

正式审计要求两份完整生产快照。开发夹具只有显式使用 `--allow-development-fixture` 时才能用于
测试。命令还会确认 `--old` 的 snapshot ID 与 `config.taxonomy.path` 实际加载的 snapshot ID
一致，防止把错误文件当作比较基线。

审计是只读操作：不修改 YAML，不建立 feed，不推进检查点，不写运行记录，也不迁移分类。

## 5. 全局分类变化

审计至少识别：

- `added`：新快照新增的分类 ID；
- `removed`：旧快照存在而新快照消失的分类 ID；
- `renamed`：同一 ID 的规范名称改变；
- `parents_changed`：父分类集合改变；
- `primary_parent_changed`：主要父分类改变；
- `active_status_changed`：活动状态改变；
- `source_url_changed`：分类来源页面改变。

父子关系由每个分类的 `parent_ids` 比较。`child_ids` 是从父关系确定性派生的缓存，不作为第二套
独立事实重复计数。

对被删除的分类，可以列出新快照中规范名称完全相同的 ID，字段名为
`exact_name_candidate_ids`。该字段只帮助人工复核，不能作为自动迁移证据。

## 6. 私人画像影响

全站可能发生大量与用户无关的变化。因此审计把下列角色分开标识：

- `confirmed`：用户已经确认的活动分类；
- `proposed`：已经核验但尚未确认的候选分类；
- `excluded`：用户明确排除的分类；
- `expanded`：旧 taxonomy 下由层级展开得到的活动分类；
- `expanded_new`：新 taxonomy 下重新展开后会进入活动范围的分类。

审计先要求当前配置能在旧快照中完整重建，并要求配置 feed 恰好覆盖旧展开集合。这个前提不满足
时，程序停止，因为此时无法区分“taxonomy 变化”与“旧配置本来就不一致”。

对新快照重新计算展开集合后，报告：

- 新进入兴趣范围的分类 ID；
- 离开兴趣范围的分类 ID；
- 新快照所需但配置尚无的 feed；
- 配置仍有但新展开集合不再需要的 feed；
- 每个受影响分类的旧名称、新名称、角色、变化类型和要求的人工动作。

待确认候选虽然不参与匹配，但仍要审计。否则 taxonomy 改名或删除后，私人配置会在正式运行的
候选核验阶段失败，或者把过时的候选继续呈现给用户。

## 7. 激活状态

### `ready`

taxonomy 可以包含与当前画像无关的全局变化，但当前确认、候选、排除和展开集合没有变化，feed
覆盖仍然精确。命令仍不自动修改配置。若用户决定启用新快照，需要：

1. 更新 `taxonomy.path`；
2. 增加 `interest.version`；
3. 写入新的带时区 `effective_from`；
4. 运行 `pfm catch-up` 登记新版不可变画像；
5. 如果 feed 集合没有变化，不重新把旧记录当成新论文。

taxonomy ID 是活动运行画像的一部分，所以即使兴趣范围未变化，启用新 taxonomy 也要创建新
画像版本，不能原地改写旧版本。

### `review_required`

稳定 ID 仍存在，但名称、层级、活动展开或 feed 覆盖发生变化。启用前必须审查影响；需要新增
feed 时先执行增量基线，把该 feed 当前条目标为历史，不能直接当作本周新作。

### `blocked`

确认分类或其他必须核验的私人分类被删除、停用，或者选中分类无法在新快照中重建。不得启用新
快照。即使出现同名新 ID，也必须由官方证据或用户审查决定是替代、拆分、合并还是无关分类。

## 8. 调度边界

当前命令行认证请求会受到 Cloudflare challenge，因此 taxonomy 更新暂时不能被描述为完全无人
值守。可行流程是用户在正常私人浏览器会话中取得官方 JSON，运行 `taxonomy-import`，再运行
`taxonomy-audit`。

在官方接口能够稳定供程序访问之前，不创建会反复失败或诱导绕过访问控制的自动刷新任务。周报
可以继续使用已经验证的旧快照；“快照较旧”应作为维护提醒，而不是关闭 TLS、复用 Cookie 或无
审计覆盖当前快照的理由。

## 9. 验收要求

- 相同快照审计结果为 `ready`，变化数为零；
- 与私人画像无关的新增分类不阻止激活；
- 活动分类同 ID 改名进入 `review_required`，且不修改配置；
- 活动分类 ID 消失进入 `blocked`；
- 同名新 ID 只列为候选，不自动迁移；
- 新后代分类能够改变展开集合并列出缺少的 feed；
- 旧快照文件不会被同 ID 异内容覆盖；
- 审计输出明确声明 `automatic_migration_performed: false`；
- 历史补跑只能使用其画像记录的已保留、重新验证通过的 taxonomy 快照。
