# 兴趣范围与资源提醒政策

## 1. 目的

本政策处理两件容易混淆的事：

1. 用户确认一个上位 PhilPapers 分类及其全部后代时，活动兴趣集合会扩大多少；
2. 这种扩大可能怎样影响分类 feed、历史基线、书目核验、报告长度和模型上下文。

系统不得把这些不同资源统一说成一个无法核实的“token 消耗”。能够在运行前确定的数量应当由
程序直接计算；依赖未来候选论文数量的成本，只能说明影响方向和安全上限，不能伪造精确值。

本政策不评价研究范围是否“太宽”，也不替研究者删除兴趣。它只要求在有实质资源影响时先提供
可理解的事实，再由用户决定维持宽范围、改选较窄分支或分阶段建立画像。

## 2. 四种必须区分的资源

### 2.1 taxonomy 展开

`selected category + descendants` 是本地确定性图遍历，不需要调用模型逐个“想出”后代，也不需要
网络请求。只要完整 taxonomy 已经存在，程序就可以准确计算展开后的分类数。

默认预估结果不打印完整后代 ID／名称列表。否则一次本来只需要几个计数的预检，反而可能制造
很长的终端输出和模型上下文。用户明确要求审查完整清单时才另行展示。

### 2.2 分类 feed 范围

当前架构为展开集合中的每个分类维护一个分类 feed。因而程序可以准确报告：

- 当前活动分类 feed 数；
- 本次新增分类 feed 数；
- 变更后的分类 feed 总数；
- 新增 feed 是否需要先建立历史基线。

“分类 feed 数”不等于精确 HTTP 请求数：实际加载可能还包括 feed 发现、重定向、重试或缓存。
因此 UI 和文档只能报告分类源范围，不能把它冒充精确网络请求账单。

### 2.3 OpenAlex／Crossref 核验工作

书目核验量取决于各 feed 当时包含多少唯一记录、日期提示和 DOI 覆盖率，以及批量身份核验能够
解决多少候选。taxonomy 本身不能预知这些数值。预检应说明“候选相关、不能事先精确计算”，并
保留 `pull-now` 的总候选上限、逐篇退回预算、批量查询和延期统计。

这里涉及的是远程 API 请求、OpenAlex credits／速率限制和运行时间，不应全部称为模型 token。
当前默认硬上界把 1000 个总候选规划为至多 20 个 DOI 批次、50 个初始题名批次且每批最多拆分
一层，再加 50 个逐篇 OpenAlex／Crossref 候选：即 OpenAlex 最多 220 个、Crossref 最多 50 个
逻辑请求。缓存命中不占逐篇远程候选预算；运行后仍以实际网络遥测和提供方返回的额度头为准。
成功的题名批量调用还会保留一小时的散列调度标记；同一批候选短时间再次拉取时不重发题名批次，
但未取得正候选的论文仍进入逐篇轮转，不会被标记为“不存在”。

题名明确带有受控多语言书评／评论前缀的记录会在远程书目查询前按共用作品类型门槛排除，因此不占
OpenAlex／Crossref 额度。这个优化只能减少有明确书目形式标签的记录，不能把没有标签、仅凭主题看似
不像论文的候选静默排除；后者仍需要来源提供的结构化类型证据。

### 2.4 模型上下文和输出 token

确定性的 taxonomy 展开和集合交集由本地 Python 完成，本身不要求模型推理。模型 token 可能在
以下情况下增加：

- 把数百个分类名称全部放进对话并逐个讨论；
- 让 Codex 阅读或解释大量候选记录；
- 生成或复核很长的即时报告／周报；
- 对跨语言作品同一性候选进行逐项语义复核。

候选数尚未产生时不能声称一个精确 token 数。提醒应写“可能增大模型上下文／输出”，并优先让
确定性程序输出计数和汇总。

即时拉取的完整 Markdown 默认内联返回。已有候选计数、先前报告字符数或明确提高的安全上限表明
输出可能很长时，应告知用户可以选择 `--report-delivery file`：完整报告仍生成并保存到私人报告
目录，但命令行只把路径、字符数和统计放入模型上下文。程序不得未经用户选择自行改变交付方式。
该选项减少的是当前对话中的报告全文，不减少 feed 范围、远程 API 核验或报告文件本身的内容。

## 3. 何时必须先提醒

在下列操作之前必须做资源说明：

- 用户要求一个上位分类包含全部后代；
- 预估将新增 11 个或更多分类 feed；
- 用户要求提高 `pull-now` 的总候选或逐篇退回安全上限；
- 用户要求在对话中枚举、解释完整 taxonomy 或一个很大的后代集合；
- 已有计数表明候选、延期项或报告会很长，需要模型进一步逐项处理。

其中 taxonomy 扩展使用以下交互闸门：

| 新增分类 feed | 范围级别 | 行为 |
|---:|---|---|
| 0—10 | `bounded` | 显示计数；继续遵守普通标签确认规则 |
| 11—50 | `broad` | 显示计数和资源影响；得到明确确认后才能修改画像或建立基线 |
| 51 以上 | `very_broad` | 不得静默启用；明确确认之外，还应提供先选较窄子分支的替代方案 |

10 和 50 是第一版的交互安全闸门，不是学术意义上的宽窄评价，也不是费用预测。以后只有在积累
真实运行数据并更新文档、测试和版本后才能调整。

## 4. 确定性预估命令

例如，预估把 `Plato`（正式 category ID `6266`）及其全部后代追加到现有画像：

```powershell
.\.venv\Scripts\pfm.exe scope-estimate `
  --config .\config\watchlist.yaml `
  --category-id 6266 `
  --include-descendants
```

该命令：

- 从私人配置读取当前确认集合，只计算净新增范围；
- 使用配置指向的 taxonomy；
- 不访问网络；
- 不修改配置、feed、基线、SQLite 或周报；
- 只输出所请求的顶层分类和各类计数，不输出完整后代清单；
- 把模型 token 标为不可由 taxonomy 预估，而不是给出虚假的精确数字。

如果还没有私人配置，可以明确提供 taxonomy：

```powershell
.\.venv\Scripts\pfm.exe scope-estimate `
  --taxonomy F:\path\to\philpapers-taxonomy.json `
  --category-id 6266 `
  --include-descendants
```

## 5. 面向用户的提醒内容

提醒至少回答以下问题：

1. 用户要求加入的上位分类是什么；
2. 它在当前 taxonomy 中展开为多少分类；
3. 扣除已经覆盖的分类后，会新增多少分类 feed；
4. 这些新增 feed 是否必须建立基线；
5. 即时拉取为什么可能增加 API 核验量和等待时间；
6. 为什么目前不能准确预报模型 token；
7. 用户可以选择全部加入、改选较窄子分支，或先查看分支摘要。

一个合格的提醒可以写成：

> 当前 taxonomy 中，`Plato` 及其后代将把画像扩展到 N 个分类，其中 M 个是相对于现有画像的
> 新增分类源。新增源需要先建立历史基线；以后的完整扫描也会覆盖这些源。实际 OpenAlex／
> Crossref 核验量和报告 token 取决于届时产生的候选论文数，现在不能准确计算。是否仍全部加入，
> 还是先选择 Plato 下较窄的分支？

提醒中不得暗示用户的研究兴趣“不合理”，也不得以节省资源为由擅自缩小范围。

## 6. 周报与即时拉取的关系

兴趣范围扩大后，周报和即时拉取都使用同一个活动分类集合，也必须使用相同的新近性、旧作／
重录、作品同一性、支持稿本类型和分类交集标准。即时拉取的批量查询、优先队列和延期预算只解决
冷启动效率；它们不得改变“哪些证据足以推送”的语义。

周报通常只核验基线之后新出现或需要重试的记录，所以宽画像的单次核验量往往小于即时冷启动；
但它仍会读取全部配置 feed。资源提醒最好在画像扩展时发生一次，而不是每周重复打扰用户。只有
某次运行实际超出安全上限、失败或覆盖不完整时，才需要再次报告。

## 7. 隐私与日志

范围预估只应输出分类 ID、分类名称和数量。不得输出用户研究方向原文、账户证据、API key、候选
论文题名或远程查询 URL。预估命令的结果可以安全地用于交互确认，但完整私人画像仍只保存在 Git
忽略的本地配置中。
