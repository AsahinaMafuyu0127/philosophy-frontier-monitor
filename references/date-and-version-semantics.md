# 时间与版本语义

状态：第 0 阶段基线初稿
最后修订：2026-09-05

## 1. 目的

本文规定项目中所有时间字段、监测事件、作品版本和版本关系的含义，防止把“数据库记录最近变化”“预印本上传”“论文正式发表”和“本系统第一次看到”混写成含义不明的“新论文”。

这些定义是数据库、去重器、采集器和报告器共同使用的语义合同。程序可以暂时不支持某些字段，但不得用一个含义不明的 `date` 字段替代它们。

## 2. 基本原则

1. 每个日期必须说明它描述什么事件；
2. 每个来源日期必须保留来源与原始值；
3. 必须保留来源提供的精度，不得补造月份、日期或时刻；
4. 来源事实与系统推断必须分开；
5. 数据源之间存在冲突时分别保存，不无痕覆盖；
6. 未知值使用 `null`，不得由语言模型猜测；
7. 报告中的“新”必须带有限定语；
8. 作品、来源条目和元数据记录是不同层次，三者的更新时间不能混同。

OAI-PMH 的 `datestamp` 是为了增量采集而提供的元数据记录时间戳，表示记录的创建、删除或最近修改；它不自动等于论文出版日期。OAI-PMH 还允许日期只有“日”或精确到秒，并统一使用 UTC。参见：

- [OAI-PMH Version 2.0 资源与规范](https://www.openarchives.org/pmh/)
- [OAI-PMH Repository Implementation Guidelines](https://www.openarchives.org/OAI/2.0/guidelines-repository.htm)

## 3. 时间值的通用结构

时间值使用下列逻辑结构：

```yaml
value: "2026-09-05T08:30:00Z"
precision: "second"
source: "crossref"
source_record_id: "10.xxxx/example"
inferred: false
retrieved_at: "2026-09-05T09:00:00Z"
```

### `precision`

允许值：

- `year`：只有年份；
- `month`：精确到月份；
- `day`：精确到日期；
- `second`：有完整时间戳；
- `unknown`：原始值存在但暂时不能可靠解析。

例如来源只提供 `2024` 时，不能保存为 `2024-01-01`。后者会虚构月、日，并在排序时制造错误的精确性。

年或月精度不能证明一项事件落在某个具体星期内。但是，如果该年份或月份的整个可能区间都早于
监测窗口，它仍足以证明作品不是本周新出。例如当前窗口在 2026 年 9 月时，`2025-04`
虽然不能还原成某一天，却可以确定为 `newly_indexed_old_work`，无需继续等待日精度证据。

### 时区

- 内部完整时间戳统一转换并保存为 UTC；
- 来源只有日期而没有时区时，保留其日期精度，不擅自附加本地时区；
- 面向用户显示时可以转换为 `Asia/Shanghai`；
- 用于增量采集的边界必须按来源协议要求计算，不能先转换为本地日期再请求。

## 4. 时间字段

| 字段 | 中文名称 | 定义 | 不表示什么 |
|---|---|---|---|
| `observed_at` | 首次观察时间 | 本系统第一次看见该来源记录或作品的时间 | 不等于上传或发表时间 |
| `retrieved_at` | 获取时间 | 本次从数据源读取响应的时间 | 不等于来源记录发生变化 |
| `source_datestamp` | 来源采集时间戳 | 来源用于增量采集的记录时间戳 | 不必然是正文修订或发表时间 |
| `deposited_at` | 存档上传时间 | 作品或版本被提交到存档的时间 | 不等于同行评议通过或正式发表 |
| `source_updated_at` | 来源更新时间 | 来源明确提供的条目更新时间 | 不必然表示正文内容改变 |
| `revised_at` | 版本修订时间 | 有证据表明论文文本版本发生修订的时间 | 不包括单纯的元数据格式变化 |
| `accepted_at` | 接受时间 | 出版方或作者明确给出的接受日期 | 不等于公开时间 |
| `published_online_at` | 在线发表时间 | 出版方首次正式在线发表的时间 | 不等于卷期归属或纸本出版 |
| `issue_published_at` | 卷期出版时间 | 作品被编入正式卷期的时间 | 不必然是首次可访问时间 |
| `published_print_at` | 纸本出版时间 | 可确认的纸质版本出版时间 | 不等于在线发表时间 |
| `last_checked_at` | 最后检查时间 | 系统最后一次检查某来源或记录的时间 | 不表示记录发生变化 |

每个作品可以同时具有多个合法日期。例如一篇论文可以在 2024 年上传预印本、2025 年被期刊接受、2026 年正式在线发表、2027 年编入纸本卷期。这些日期不得相互覆盖。

## 5. 监测事件

监测报告和内部事件记录使用下列受控值。

### `newly_observed`

本系统第一次看见一条来源记录或一个作品。

它可能是一篇近期论文，也可能是一篇刚被数据库收录、刚进入用户监测范围或此前漏采的旧论文。没有其他时间证据时，只能报告“本系统首次发现”，不能写“刚发表”。

### `recently_deposited`

来源明确显示某个版本近期上传到存档。它描述上传行为，不表示正式出版或同行评议状态。

### `recently_arrived_in_philpapers_alert`

作品以新材料身份出现在 PhilPapers 当前页面提醒流中，并且本程序完成旧作检查后没有发现更早的
同一作品记录。该事件对应 `freshness_status = confirmed_source_arrival`，可用于及时交付手稿、
working paper、预印本、作者接受稿和 forthcoming 文章。它只断言“新近进入研究者可见的来源
提醒流”，不等于论文在该日正式发表，也不把本机抓取时刻改写成来源声称的首次公开日期。

### `recently_published_online`

有出版方、Crossref 或其他可核验来源表明作品近期正式在线发表。报告应同时给出来源和日期精度。

### `recently_assigned_to_issue`

作品近期获得正式卷、期、页码或文章号。它可能晚于首次在线发表。

### `source_record_updated`

来源元数据记录发生变化，但尚不能确认论文正文发生修订。OAI `datestamp` 变化在没有额外证据时应归入此类。

### `revised`

可以确认已有版本的论文正文出现新版本或实质修订。系统应保存旧版本信息和新版本关系，不能只覆盖原记录。

### `rediscovered`

系统因新增数据源、扩大监测范围、修复历史故障或来源重新收录而再次发现一篇旧作品。它不是新的发表事件。

### `version_linked`

系统新确认了两个此前分离记录之间的版本关系，例如预印本与正式出版版本的对应关系。

### `record_deleted_at_source`

来源明确标记记录已删除。系统可以停止把该来源记录视为当前有效，但不得据此推断作品已经撤回、被否定或从所有来源消失。

## 6. 报告用语

禁止在没有限定的情况下单独使用“新论文”。根据证据选择下列用语：

- “本系统于本周首次发现……”；
- “该预印本于本周上传至……”；
- “该手稿本周新近进入 PhilPapers 提醒流；未发现更早作品证据，正式发表日期尚未记录……”；
- “该论文于本周正式在线发表……”；
- “该论文于本周被编入第 X 卷第 Y 期……”；
- “来源元数据于本周更新，正文是否修订尚未确认……”；
- “此前发现的预印本现已确认对应正式出版版本……”；
- “该旧作因监测范围扩展而被重新发现……”。

如果证据只能支持 `newly_observed`，不得为了使报告显得更及时而改写为 `recently_published_online`。

## 7. 版本类型

`version.type` 允许下列值：

| 值 | 含义 |
|---|---|
| `preprint` | 同行评议前公开的稿本 |
| `submitted_manuscript` | 已投稿但尚无接受证据的版本 |
| `author_accepted_manuscript` | 已获接受但不一定具有出版方排版的作者稿 |
| `proof` | 校样或出版前排版版本 |
| `version_of_record` | 出版方认定的正式记录版本 |
| `revised_preprint` | 有明确版本序列的修订预印本 |
| `conference_version` | 会议发表或会议论文版本 |
| `book_chapter_version` | 作为书籍章节发表的版本 |
| `translation` | 与另一语言版本存在翻译关系的文本 |
| `unknown` | 当前证据不足，不能可靠判断 |

版本类型描述载体和出版状态，不等于哲学质量等级。

## 8. 版本关系

版本关系必须有方向。允许值包括：

- `is_version_of`：本记录是另一作品或记录的一个版本；
- `has_version`：本记录具有另一个版本；
- `replaces`：本版本明确取代较早版本；
- `is_replaced_by`：本版本被较新版本取代；
- `is_published_as`：稿本后来以另一记录正式出版；
- `has_preprint`：正式版本具有已确认的预印本；
- `is_translation_of`：本作品是另一语言作品的翻译；
- `same_work_uncertain`：有理由怀疑属于同一作品，但证据不足；
- `related_work`：有明确相关性，但不是版本关系。

关系记录至少应包含：

```yaml
relation_type: "is_published_as"
target_record_id: "pfm:work:..."
confidence: "high"
evidence:
  - source: "crossref"
    description: "shared DOI reported by publisher metadata"
decided_by: "system"
decided_at: "2026-09-05T08:30:00Z"
```

## 9. 版本关系证据

### 可以支持自动确认的强证据

- 相同、有效且无冲突的 DOI；
- 出版方或存档明确提供的版本关系；
- 作者主页明确将预印本链接到正式出版记录；
- 来源提供的规范关系字段。

### 只能产生候选关系的弱证据

- 题目高度相似；
- 作者列表大致相同；
- 摘要内容高度相似；
- 发表年份接近；
- 一个记录提到另一个记录的题目。

标题相似不能单独证明版本关系。哲学论文可能使用相同或高度相似的题目，翻译也可能改变题目形式。

## 10. 冲突与不确定性

当来源给出互相冲突的日期或版本类型时：

1. 保存所有来源值；
2. 记录每个值的抓取时间；
3. 不修改原始值；
4. 规范显示值可以依据来源优先规则选择；
5. 显示值的选择必须保留理由；
6. 冲突会影响“是否近期”的判断时，进入人工复核；
7. 在复核前使用保守报告用语。

## 11. 增量监测的时间边界

- 每个来源分别维护检查点，不能共用一个全局时间；
- 检查点记录的是最后一次完整成功的来源边界；
- 分页未完成时不推进检查点；
- 请求窗口应有可配置的重叠，以吸收来源延迟和边界精度问题；
- 重叠产生的重复记录由稳定来源 ID 和去重机制处理；
- 来源提供 `responseDate`、游标或分页令牌时，应保存完成恢复所需的信息；
- 系统时钟与来源时钟不能假定完全一致。

原则上，宁可在重叠窗口中再次看到一条记录，也不能因过早推进检查点而永久漏掉它。

## 12. 即时拉取的滚动时间边界

用户主动请求即时拉取时，默认窗口不是“上一完整自然周”，也不受固定周报星期与 08:00 交付
时刻约束。它以用户请求的准确时刻为 `window_end`，在用户配置时区中向前推七个当地日得到
`window_start`，再把两个边界转为 UTC 比较：

```text
[local_request_time - 7 local days, local_request_time)
```

“当地日”意味着跨越夏令时切换时保持相同的当地墙上时刻，因此实际 UTC 时长可能是 167、168
或 169 小时。用户显式指定 `--days` 时允许 1—31 日，仍采用同一半开区间。

即时窗口与周窗口可能重叠，且没有跨报告唯一性约束。同一个 `publication_event` 同时落在即时
窗口和后来正式周窗口中时，两份报告都可以列出它；这不是把事件日期改写了两次，也不是同一
正式周窗口重复提交。即时报告不得生成 `notification` 或推进检查点。

RSS／Atom 条目日期在即时模式中只是候选选择时间，必须与作品时间严格区分：

- `feed_candidate_time`：来源 feed 提供的 `pubDate`、`published` 或 `updated`，只决定是否值得
  发起本次书目核验，也可以在旧作检查完成后保存为来源提醒时间，但不成为出版日期；
- `feed_candidate_year`：当真实 RSS 没有时间字段时，从 description 开头书目串提取的第一个
  独立四位年份，只能把候选限制到与窗口相交的年份；其精度不足以证明七日窗口内新出；
- `source_datestamp`：PhilArchive OAI header 的记录创建、修改或删除时间。PhilArchive 当前提供
  秒级粒度，增量收割必须向前重叠一秒、完整跟随 `resumptionToken`，并把包含式 `until` 对齐为
  半开窗口末端前的最后一个完整秒，再在本地按精确半开窗口过滤；它只能证明
  来源记录在窗口内变化，不能证明作品在窗口内发表；
- `publication_date`：Crossref、OpenAlex、出版方或经批准来源给出的作品发表／公开日期，进入
  `confirmed_new` 判断；允许在 `confirmed_source_arrival` 记录上保持为 `null`；
- `availability_date`：作品新近进入 PhilPapers 当前提醒流的来源时间；没有来源条目时间时，只能
  保存本次 `observed_at` 并明确标注为本机观察，不能称为首次发表或首次上传；
- `request_time`：用户触发即时拉取的时刻，只定义窗口右端；
- `observed_at`：程序读取 feed 的时刻，不证明发表。

程序不得把 `feed_candidate_time`、`feed_candidate_year`、`source_datestamp` 或 `observed_at`
复制到 `publication_date`，也不得在报告中把它们称为“首次发表日期”。feed 时间与年份都缺失
时，成功且完整的 OAI 窗口收割可以作为即时模式的正面候选门槛：同一 `/rec/` 记录在窗口内发生
变化才继续核验，未命中只从本次滚动候选集移除，不形成永久的 `not_new` 判断。若 OAI 失败或
不完整，则不能依据未命中排除，必须回退到宽候选并披露覆盖失败。外部出版日期存在时形成
`confirmed_new`；外部数据库查无记录而非访问失败、且旧作检查没有发现更早证据时，可以形成
`confirmed_source_arrival`。

已经完整收割的 OAI 区间可以保存到与周报状态分离的私人跨运行缓存。缓存覆盖只有在分页完整成功
后才成立；命中缓存仍重新执行当前窗口和 `/rec/` 交集。缓存中的 `source_datestamp` 不因持久化而
获得出版日期含义，删除标记也必须在较新记录覆盖较旧活跃记录时生效。
